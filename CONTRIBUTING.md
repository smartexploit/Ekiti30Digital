# Contributing to EKITI@30 DIGITAL

Thank you for contributing to **EKITI@30 DIGITAL — Our Story. Our People. Our Future.**

EKITI@30 DIGITAL is a collaborative project. Every contribution should help build an accurate, useful, accessible, and continuously growing digital record of Ekiti State.

## 1. Our Working Principle

Every member owns a defined area of the project.

Ownership does not mean working alone. Members are expected to collaborate when their areas overlap.

Before making major changes, communicate with the relevant project lead.

## 3. Contribution Workflow

All significant work should follow this workflow:

**BACKLOG → READY → IN PROGRESS → REVIEW → APPROVED → DONE**

### BACKLOG

The task has been identified but work has not started.

### READY

The task has enough information to begin.

### IN PROGRESS

A member is actively working on the task.

### REVIEW

The work has been completed and needs to be checked.

### APPROVED

The work has passed the required review.

### DONE

The work has been integrated into the project.

## 4. Research Contributions

When adding factual information about Ekiti State, contributors should record:

* The information being added.
* The source.
* The source type.
* The relevant date or time period.
* Any important context or limitations.

Whenever possible, use credible sources such as:

* Government publications
* Official institutional websites
* Academic publications
* Books and archival materials
* Reputable news organizations
* Established cultural or historical institutions
* Verified primary documents

Do not present an unsupported claim as an established fact.

## 5. Citizen Stories

Citizen stories are welcome and valuable.

Personal memories, experiences, oral histories, photographs, and community accounts should be clearly identified as citizen contributions where they have not been independently verified.

A personal account should not automatically be presented as an independently established historical fact.

## 6. AI-Generated Content

AI tools may assist with:

* Research organization
* Drafting
* Summarization
* Data structuring
* Coding
* Content analysis
* Knowledge-base preparation

However, AI output is not automatically considered a verified source.

Factual claims must be checked against appropriate source material before being published as factual information.

## 7. Code Contributions

Code changes should:

* Be related to an approved project task.
* Follow the existing project structure.
* Avoid unnecessary changes to unrelated files.
* Be tested before submission where practical.
* Include clear commit messages.
* Be reviewed before being merged into the main branch when review is required.

## 8. Commit Messages

Use short and descriptive commit messages.

Examples:

```text
Add Ekiti LGA dataset
Add initial historical timeline
Create Ask Ekiti API structure
Add homepage layout
Add citizen story submission form
Update knowledge base schema
Fix timeline rendering
```

Avoid vague messages such as:

```text
Update
Changes
Fix stuff
New work
```

## 9. Pull Requests

For significant code changes, contributors should create a pull request instead of directly modifying the main branch.

A pull request should explain:

* What was changed.
* Why it was changed.
* What task it addresses.
* How it was tested.
* Any known limitations.

## 10. Content Review

Content should be reviewed before being treated as verified project knowledge.

Review should consider:

1. Accuracy
2. Source credibility
3. Date and context
4. Consistency with existing information
5. Whether the content is factual, interpretive, or personal
6. Whether additional verification is required

## 11. Data Quality

Avoid duplicate, contradictory, outdated, or unsupported information.

When conflicting sources exist, document the disagreement rather than silently choosing one without explanation.

## 12. Respectful Collaboration

All contributors are expected to:

* Communicate respectfully.
* Give credit to contributors and sources.
* Accept constructive feedback.
* Avoid unnecessary conflicts.
* Raise concerns early.
* Keep project discussions focused on improving the work.

## 13. Project Direction

The project is designed to continue beyond the initial launch sprint.

The first week establishes the foundation, but research, development, verification, community contributions, and feature development will continue as the platform grows.
